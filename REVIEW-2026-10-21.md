## Новые находки

### WARN

**W1'. `OwnerCommandsService.java:104-122` — /banlist может превысить лимит Telegram 4096 символов, и админ не получит НИЧЕГО**
Строка с длинным username: `• @<32 символа> (id=<13 цифр>) — чат -1001234567890 — с 2026-10-21T18:33:22.123Z`
≈ 105–110 символов. При 50 записях (BANLIST_LIMIT) — 5300+ символов → `sendMessage` бросит
`TelegramRequestException`, список не уйдёт целиком, в логе только ERROR. Тест
`longBanlistIsCapped` это не ловит: usernames короткие («user1»), а ограничение по количеству
срабатывает до переполнения длины.
**Фикс:** формировать текст с контролем длины, отправлять чанками ≤ ~3500 символов
(BANLIST_LIMIT=50 оставить вторичным ограничением). Тест с длинными username (32 символа).

**W2'. `AdminRegistry.java:46-56` — в ветке «протухший кеш + сбой API» нет negative-cache, и сбой глотается молча**
Unknown-cache (15с) ставится только при `cached == null`. Если кеш реальный, но протух, а API
лежит — **каждый** `isAdmin` (т.е. каждое сообщение группы) дёргает `GetChatAdministrators`
и молча глотает исключение (ни warn, ни debug). Час недоступности API при активном чате —
тысячи бесполезных вызовов, съедающих общий rate-limit бота (429 начнут ловить и ban/sendMessage).
**Фикс:** логировать сбой (warn не чаще раза в TTL); при желании обновлять `fetchedAt`
«неизвестно»-семантики, не подменяя протухшие реальные данные.

**W3'. `CaptchaService.java:200-244` — гонка expireOne ↔ верный ответ: PASSED-юзер получает перманентный бан**
Планировщик и polling-поток работают параллельно. `expireOne` проходит проверку `expiresAt`,
затем делает ДВА сетевых вызова (`getChatMemberStatus`, затем `enforcement.ban` — секунды).
Если в этом окне юзер нажал верную кнопку: `handleCallback` снимет сессию, запишет PASSED,
покажет «✅ Принято» — а вернувшийся из API `expireOne` всё равно вызовет `ban` уже
прошедшего юзера (в т.ч. перезапишет БД на BANNED). Окно мало, цена максимальна, сценарий
реален: юзеры часто отвечают на границе 5 минут, тик планировщика — 30с.
**Фикс:** после проверки статуса и ПЕРЕД `enforcement.ban` убедиться, что сессия всё ещё
в карте (`sessions.get(key) == session`), или снимать её двухаргументным `remove(key, session)`
до наказания (при сбое бана — вернуть через `putIfAbsent`; ретрай-логика `banAttempts`
сохраняется). Тест: «верный ответ во время expireOne отменяет бан».

**W4'. `DotenvEnvironmentPostProcessorTest.java:88-95` — тест зависит от локального секретного файла, сьют невоспроизводим**
`existingEnvFileIsFoundInWorkingDirectory` требует реального `.env` с непустым `BOT_TOKEN` в
рабочей директории. Сейчас он есть — зелёный; на чистой машине/в CI (`.env` в git не попадает)
**гарантированно красный**. Логика `load()` полностью покрыта остальными пятью тестами.
**Фикс:** тест удалить; поиск `.env` в CWD при желании покрыть интеграционно, без секретов.

### NIT

- **N1'.** `LinkDetector.java:40` — entity-тип `text_mention` (скрытое упоминание пользователя
  без username) не детектируется: `SUSPICIOUS_ENTITY_TYPES` = `url|text_link|mention` c
  `matches()`. Дополнить до `url|text_link|text_mention|mention`.
- **N2'.** `LinkDetector.java:34-36` — в TLD-списке нет «ком/орг/нет/инфо» (кириллические
  транслитерации): «заходи на сайт.ком» — самый частый RU-вариант — проходит. Дёшево добавить.
- **N3'.** `DotenvEnvironmentPostProcessor.java:52-58` — строка `export KEY=VALUE` парсится в
  ключ «export KEY» (тихо нерабочая переменная: бот молча стартует без токена); inline-комментарий
  `KEY=VALUE # comment` попадает в значение (в docker-compose env_file — отрезается:
  расхождение локальный запуск vs контейнер); javadoc-опечатка «ANTI SPAM_ENABLED» (строка 18).
- **N4'.** `UpdateRouter.java:118-119` — callback по неактуальному сообщению (message не Message)
  игнорируется без `answerCallbackQuery` → у юзера «часики». Ответить, если `callbackQueryId` есть.
- **N5'.** `CaptchaService.cancelSession:259-262` — `DELETE_FAILED` на ERROR при том, что
  комментарий сам объясняет: это штатный случай («уже удалено при бане»). Понизить до warn/debug.
- **N6'.** `CaptchaService.expireOne` — статусы `kicked`/`administrator`/`creator` обрабатываются
  как «в чате»: kicked → идемпотентный повторный бан + лишнее уведомление; administrator →
  3 бесполезных ретрая + 3 banFailed-уведомления + BAN_GAVE_UP. Добавить в ветку пропуска.
- **N7'.** `OwnerCommandsService`: редактирование команды владельцем в личке ре-исполняет её
  (edited_message → ветка владельца) — двойной /banlist и т.п. Безвредно, но можно игнорировать
  edited-сообщения в личке владельца.
- **N8'.** `handleCallback` не проверяет `expiresAt` — опоздавший верный ответ принимается, пока
  сессия жива (штатно ≤30с grace + задержка тика). Задокументировать в javadoc как осознанный grace.
- **N9'.** `AdminNotifierImpl` при `adminChatId<=0` делает `return` ДО своих строк `VIOLATION`/
  `BAN_FAILED` в логе — аудит в нотификаторе пропадает (аудит-трейл выживает за счёт логов
  `EnforcementService`, но связка хрупкая). Логировать до проверки.
- **N10'.** Инфраструктура: `scripts/smoke.sh` проверяет лишь существование файла `antispam.db`
  (создаётся SQLite и без таблиц — заявленная в шапке проверка `schema.sql` не выполняется;
  добавить `sqlite3 .tables` или запрос); compose-healthcheck `pgrep -x java` — только
  liveness процесса, зависший polling не детектирует (минимум осознанный; отметить в комментарии).
- **N11'.** Остатки прежних: `Participant.java:70,75,90` — `Instant.now()` мимо `Clock` (N2);
  `@Version` нет (N1); **первого коммита в git по-прежнему нет** (N8 — напоминание: делается
  по явной команде владельца).

## Что хорошо (не трогать)

- Связка «бан за ссылку → `cancelSession`» и отказ от капчи при `banned=false` (в т.ч. порядок
  «сначала модерация, потом капча» в роутере).
- `EnforcementService.ban → boolean` с созданием BANNED-записи «с холодного старта» — /banlist
  и /unban видят всех забаненных.
- Идемпотентность разбана: `only_if_banned=true`, переживание сбоя delete записи, повторный /unban.
- Владелец-чек в обоих новых путях (`chatId==adminChatId && fromId==adminChatId`), чужие
  callback-и получают ответ «не для вас», `adminChatId=0` безопасен по умолчанию.
- Fail-open в `AdminRegistry` честно задокументирован и оттестирован (вкл. восстановление).
- Ретраи бана с конечным лимитом; изоляция сбоев в `expireSessions` (одна сессия не роняет тик).
- `.env` закрыт со всех сторон (git, docker-контекст, права 600); `DotenvEnvironmentPostProcessor`
  с правильным приоритетом (env > .env > yml) и тестом на это.
- smoke.sh: podman/docker, SELinux-метка `:Z` — внимание к Bazzite.
- DEPLOY §7: предупреждение «снял админку — модерация молча перестанет работать».
