# Дисциплина (глобальные правила — мастер-копия)

Эти правила действуют во ВСЕХ проектах. В любом проекте, где используются наши
инструменты (opencode + скиллы из `~/.agents/skills/`), правила должны быть
перенесены в `.opencode/AGENTS.md` этого проекта (секцией «Дисциплина», целиком,
без пересказа). Делается при первой настройке проекта или первой сессии в нём;
актуальный текст — здесь, при расхождении проектов источник истины — этот файл.

- **Файлы — только инструментами файловой системы** (write/edit). Создавать и править файлы через Shell (`echo >`, `cat <<EOF`, `sed -i`, `tee` и т.п.) запрещено. Shell — для запуска команд и проверки состояния.
- **Верификация = запуск и наблюдаемое изменение состояния.** Чтение кода проверкой не считается: «прочитал — должно работать» — не результат. Проверил = видел изменение состояния (тесты красные → зелёные, endpoint вернул ожидаемое, файл/лог изменился). Не смог проверить — сказать об этом прямо и остановиться; не выдавать непроверенное за готовое.
- **Не инструментировать поставляемый код ради проверяемости.** Запрещено править файл, чтобы его стало проще проверить: отладочные глобалки, экспорты/хуки, добавленные «чтобы посмотреть», тестовые лазейки. Код проверяется в том виде, в каком поставляется; непроверяемость — проблема дизайна, решается рефакторингом, а не встраиванием ходов для тестов.
- **Фича — сначала аналитик-планировщик, потом код.** Запрос на новую фичу начинается с запуска субагента «аналитик-планировщик»: он в интерактивном режиме (вопросы пользователю) уточняет требования и выдаёт план работ. TDD-цикл стартует только после явного подтверждения плана пользователем; ответы на вопросы и молчаливое продолжение подтверждением не считаются. Багфиксы идут сразу в TDD-цикл.
- **TDD-дисциплина: тесты → красный → реализация → зелёный.** Фича или фикс начинаются с тестов под новое поведение. Красный прогон обязателен: новые тесты должны упасть по ожидаемой причине — показать какие и почему. Реализация — минимальная, только до зелёного; затем полный сьют зелёным. Писать реализацию раньше тестов запрещено.
- **Авто-ревью субагентом после зелёного прогона.** Если в проекте определён ревьюер-субагент — прогонять через него дифф, устранять blocker/warn-замечания и повторять прогон тестов. Ревьюер работает только на чтение: edit запрещён, bash — только `git status/diff/log/show`. Итог работы — одним сообщением: что сделано, тесты (было → стало), вердикт ревью.
- **Авто-пентест субагентом после зелёного прогона.** После ревью дифф прогоняется через субагента «пентестер» (известные уязвимости и дыры в безопасности); blocker-находки обязательны к устранению с повторным прогоном тестов. Полный аудит репозитория — по явному запросу.
- **Финал работы — Docker-образ для ручной проверки.** Любая работа завершается сборкой Docker-образа из итогового кода: человек проверяет результат руками перед коммитом. Образ обязателен, даже если задание явно звучит «написать код и закоммитить»: сначала сборка образа и ручная проверка человеком, коммит — только после неё. Если в проекте есть Dockerfile/compose — собери образ (docker или podman, как принято в проекте) и укажи в итоговом сообщении тег образа и команду запуска для проверки. Если Dockerfile нет — прямо укажи в итоге: «образ не собран: в проекте нет Dockerfile».
- **Коммиты — только по явной просьбе.** Не коммитить, не пушить и не править историю без прямого указания пользователя.
