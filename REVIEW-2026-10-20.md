## BLOCKER

### B1. Служебные сообщения не фильтруются → вышедший из группы человек перманентно банится
`src/main/java/ru/kbovyrin/antispam/telegram/UpdateRouter.java:45-71`

`handleMessage` пропускает в сервисы **любой** `message` с живым `from` и без `sender_chat`.
Служебные сообщения (`left_chat_member`, `new_chat_members`, `new_chat_title`, `pinned_message`, …)
приходят именно как `message`, `from` = сам пользователь, `sender_chat` = null. Цепочка:

1. Пользователь выходит из группы → `left_chat_member` от него самого.
2. `CaptchaService.handleFirstMessage` создаёт `PENDING`-участника и отправляет капчу
   человеку, которого в чате уже нет.
3. Через 5 минут `CaptchaExpiryScheduler` → `EnforcementService.ban` → `banChatMember`.
   Telegram молча добавляет отсутствующего в чёрный список, БД получает `BANNED` навсегда,
   админу уходит «провалена капча (истекло время)».

Итог: реальный человек, просто покинувший группу обсуждения, **навсегда теряет возможность
комментировать канал** (механизма разбана в боте нет), админ получает мусорные уведомления.
Заодно капча выдаётся на сообщении о *входе*, что расходится с README («на первое сообщение»).

**Как чинить:**
- В `handleMessage` игнорировать service-сообщения: пропускать, если заполнены
  `getNewChatMembers()`, `getLeftChatMember()`, `getNewChatTitle()`, `getNewChatPhoto()`,
  `getDeleteChatPhoto()`, `getPinnedMessage()`, `getVideoChatStarted()` и пр. — либо выдавать
  капчу только на сообщения с контентом (текст/медиа).
- Дополнительно (защита в глубину): перед баном по таймауту проверять, что юзер ещё в чате
  (например, `getChatMember`), или не банить, если с момента выдачи капчи он выходил.

**Критерий приёмки:** тест «service-сообщение (`left_chat_member`/`new_chat_members`) не создаёт
участника и не отправляет капчу» — сейчас этого поведения не фиксирует ни один тест.

## WARN

### W1. Бан по ссылке никак не связан с капчей: дубли банов и уведомлений
`UpdateRouter.java:66-70` + `CaptchaService.java:96-118,153-160`

- Первое сообщение новичка со ссылкой: `LinkModerationService` банит (запись в БД ещё не
  существует — она только обновляется), затем роутер всё равно вызывает `handleFirstMessage` →
  создаётся `PENDING` и капча отправляется уже забаненному. Через 5 минут — повторный бан,
  второе уведомление админу, `DELETE_FAILED` в логах.
- `PENDING`-юзер с активной капчей постит ссылку: бан по ссылке, но сессия остаётся в `sessions`,
  сообщение с кнопками висит в чате, при истечении — второй бан + второе уведомление.

**Как чинить:** `LinkModerationService.handle` возвращает факт бана; роутер не доходит до капчи.
Добавить `CaptchaService.cancelSession(chatId, userId)` и вызывать из пути бана (в т.ч. из
`EnforcementService` или рядом).

### W2. Сбой API без кеша → админа можно перманентно забанить; нет negative-cache
`src/main/java/ru/kbovyrin/antispam/moderation/AdminRegistry.java:42-48`

`cached == null → return false`: если `getChatAdministrators` упал в первые 60 с после старта
или после простоя чата дольше TTL, админ считается обычным юзером → админ постит ссылку →
перманентный бан без механизма разбана. Цена ошибки несопоставима с пропуском спама на время сбоя.
Плюс при недоступном API **каждое** сообщение порождает вызов GetChatAdministrators + исключение
(negative-cache отсутствует).

**Как чинить:** fail-open для этого узла (при сбое без данных — не наказывать, а для капчи можно
оставить текущее поведение), либо кешировать «неизвестно» на 10–30 с. Решение зафиксировать тестом
и комментарием. Внимание: тест `AdminRegistryTest.apiFailureWithoutCacheReturnsFalse` сейчас
закрепляет опасное поведение — при изменении его нужно переделать.

### W3. Сессия капчи удаляется ДО успешного бана: при BAN_FAILED наказание теряется
`src/main/java/ru/kbovyrin/antispam/captcha/CaptchaService.java:130,144,155-157`

`sessions.remove(...)` выполняется до `enforcement.ban()`; при сбое API тот лишь логирует
`BAN_FAILED` — сессия уже потеряна, ретрая не будет. Самоисцеление — только если юзер сам
напишет снова. Та же схема в `handleCallback` при неверном ответе.

**Как чинить:** удалять сессию после успешного бана (или возвращать в карту при ошибке с лимитом
попыток). Тест: «при BAN_FAILED в expireSessions сессия сохраняется и повторяется».

### W4. Long polling не закрывается при остановке приложения
`src/main/java/ru/kbovyrin/antispam/telegram/PollingBootstrap.java:42`

Результат `registerBot` (BotSession) никем не хранится, `stop()`/`@PreDestroy` нет. Потоки
`DefaultBotSession` не останавливаются при закрытии контекста → JVM висит до SIGKILL, при каждом
`docker compose up -d --build` возможна потеря/повтор обработки апдейта. Без `stop_grace_period`
в compose дефолтные 10 с усугубляют проблему.

**Как чинить:** сохранить сессию в поле, добавить `@PreDestroy` с `session.stop()`; в
`docker-compose.yml` добавить `stop_grace_period: 30s` и healthcheck. Проверить daemon-статус
потоков `DefaultBotSession` в 6.9.7.1.

### W5. Обход модерации: голые домены и IDN не детектируются
`src/main/java/ru/kbovyrin/antispam/spam/LinkDetector.java:18-23`

«заходи на example.com», «мой-канал.site» без схемы и «сайт.ру» (кириллический IDN) не дают
url-entity и не матчатся regex (`https?://`, `www.`, `t.me/`). Спам проходит без бана.

**Как чинить:** добавить паттерн bare-домена с закрытым списком TLD
(`\b[a-z0-9-]{2,}(\.[a-z0-9-]+)*\.(com|net|org|ru|su|ua|by|io|me|xyz|top|online|site|...)\b`)
— открытый `\.[a-z]{2,}` нельзя, зацепит имена файлов. Решение по IDN (punycode/кириллица)
принять и задокументировать. Обновить `LinkDetectorTest`.

### W6. Бэкап живого SQLite-файла tar'ом может дать битую копию
`DEPLOY.md:157-167`

Бэкап выполняется без остановки бота: копия файла посреди записи может быть несогласованной
(восстановление, в отличие от бэкапа, корректно делает `stop`).

**Как чинить:** либо `docker compose stop` перед tar (симметрично restore), либо бэкапить через
`sqlite3 /data/antispam.db ".backup ..."` / `VACUUM INTO`. Нюанс: `sqlite3` есть в образе
`keinos/sqlite3` или `alpine` + `apk add sqlite`.

### W7. README вводит в заблуждение про локальный запуск: `spring-boot:run` не читает `.env`
`README.md:32-37`

`./mvnw spring-boot:run` **не** подхватывает файл `.env` (это не docker compose). Без экспорта
переменных вручную (`export $(grep -v '^#' .env | xargs)`) приложение упадёт на проверке токена
или молча стартует с `GROUP_IDS` пустым.

**Как чинить:** поправить README — дать команду экспорта перед запуском или указать
`spring-boot.run.environmentVariables`. Заодно: `chmod 600 .env` локально и на VPS
(сейчас файл создают с правами 644 — токен читается всеми пользователями машины; в DEPLOY.md
про это ничего нет).

### W8. Нет smoke-проверки сборки Docker и работы на файловой SQLite
Тесты гоняют только `jdbc:sqlite::memory:`; собираемость Dockerfile и применение `schema.sql`
на файловой БД в volume не проверяются нигде (CI отсутствует). Права пользователя `bot` на
named volume зависят от докера на конкретной машине.

**Как чинить:** минимальный CI (GitHub Actions): `mvn verify` + `docker build` + smoke-запуск
с `ANTISPAM_ENABLED=false` и проверкой лога «Бот отключён».

### W9. Целостность Telegram↔БД при сбоях
`src/main/java/ru/kbovyrin/antispam/moderation/EnforcementService.java:62-71`

Если `repository.save` падает после успешного `banChatMember` (SQLITE_BUSY и т.п.),
`adminNotifier.violation` не вызывается, в БД остаётся `PENDING` — несогласованность без
сигнала (только общий error в `BotUpdateReceiver`). Также при бане сначала удаляются сообщения
и только потом бан: при BAN_FAILED контент для ручной проверки админом уже потерян
(в уведомлении только причина). Минимум — задокументировать порядок; в идеале — сначала
пытаться банить, потом удалять сообщения.

## NIT

- **N1.** `Participant.java:83-86` — нет `@Version`: гонка `handleFirstMessage` (прочитал PENDING)
  ↔ `expireSessions` (записал BANNED) может сохранить PENDING поверх BANNED. Вероятность мала
  (один handler-поток + scheduler), самоисправляется при следующем таймауте.
- **N2.** `CaptchaExpiryScheduler.java:22` и `Participant.java:70,85` — `Instant.now()` мимо бина
  `Clock`: часть кода на управляемых часах, часть на системных.
- **N3.** `CaptchaService.java:114-115` — микрогонка: между `sendMessage` и `sessions.put` юзер
  теоретически успеет ответить → получит «Время капчи истекло», а зомби-сессия потом забанит.
  Окно микросекундное; лечится put'ом до отправки + cleanup при ошибке отправки.
- **N4.** `CaptchaService.handleCallback:136-139` — если записи участника нет в БД, юзеру
  рисуется «✅ Принято», но PASSED не сохраняется → на следующем сообщении капча заново.
  Стоит логировать warning.
- **N5.** `BotUpdateReceiver.java:44` — в ERROR пишется весь `Update` (весь текст сообщений людей
  в логах). Достаточно `update.getUpdateId()` + класс исключения/stacktrace.
- **N6.** `application.yml:25` + `AdminNotifierImpl.java:33` — при дефолтном `ADMIN_CHAT_ID=0`
  каждый бан даёт ERROR «Не удалось отправить уведомление». Пропускать отправку при
  `adminChatId <= 0` и предупреждать один раз при старте.
- **N7.** `Dockerfile:7` — `COPY mvnw ./` не нужен (build-стадия использует системный `mvn`).
  Плюс `target/*` glob в `COPY --from=build` может подхватить несколько jar — лучше фиксировать
  имя артефакта (`-DfinalName`).
- **N8.** Git-репозиторий инициализирован, но **ни одного коммита** — вся история и текущее
  состояние не зафиксированы (риск потери, rsync вместо VCS). Исполнителю: после исправлений
  сделать первый коммит (по явной просьбе владельца).

Что хорошо и не трогать: проверка владельца callback (`parsed.userId() != userId`) и ответ
`answerCallbackQuery` во всех ветках; `.env` закрыт и в `.gitignore`, и в `.dockerignore`
(в контекст сборки не попадает — проверено); pool=1 корректен для SQLite-однописателя;
`schema.sql` идемпотентен и синхронен с `CHECK`-констрейнтом; автопересылки канала
(`sender_chat`) и анонимные админы отфильтрованы; тесты проверяют поведение через контракты.
Бот получает все сообщения только потому, что сделан админом (это же обходится privacy mode) —
это косвенно покрыто README/DEPLOY, но стоит добавить в DEPLOY.md строку «если снять админку,
модерация молча перестанет работать».

## Что НЕ покрыто тестами (приоритет для новых тестов)

1. **`TelegramBotAdapter` — 0 тестов.** Единственный слой над реальной библиотекой: маппинг
   `SendMessage`/`EditMessageText`/`DeleteMessage`/`BanChatMember`, оборачивание ошибок в
   `TelegramRequestException`, возврат messageId.
2. **`UpdateRouter`:** service-сообщения (место blocker B1); callback в чужом чате;
   `callback.getMessage() == null`; `message.getFrom() == null`; `sender_chat` у edited-сообщения.
3. **`CaptchaService`:** мусорные callback_data (`"captcha:abc:1"`, `"captcha:42"`, `"captcha:42:x:y"`);
   поведение при BAN_FAILED (W3); сценарий «ссылка-бан ↔ активная капча» (W1); сверка того, что
   `keyboard()` генерирует callback_data, корректно парсящиеся `parse()`.
4. **`PollingBootstrap`:** три ветки (enabled=false, пустой токен → fail-fast, пустой GROUP_IDS → warn).
5. **`BotUpdateReceiver`:** исключение из роутера не убивает polling-цикл.
6. **`CaptchaExpiryScheduler`** — 0 тестов.
7. **Инфраструктура:** docker build + запуск на файловой SQLite (см. W8).
